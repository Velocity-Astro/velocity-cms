# Velocity CMS — Agent Guide

Instructions for AI coding agents and people working in this repo.

## Stack

TypeScript (strict) · Zod 4 · web-standard `Request`/`Response` · Better Auth · Drizzle + libSQL (SQLite) · Astro 7 · React 19 · React Aria Components · Tailwind CSS v4 · Storybook 10 · Vitest · Node ≥22.23.4 · pnpm 10

## Commands

| Task | Command |
|---|---|
| Everything, before a commit | `pnpm validate` (lint → build → test) |
| Build and type-check | `pnpm build` |
| Tests | `pnpm test` (builds first: packages import each other's `dist`) |
| Lint | `pnpm lint` (ESLint, then the design system's rules) |
| Design system showcase | `pnpm --filter @velocity-astro/cms-ui storybook` |
| Accessibility of every story, light and dark | `pnpm --filter @velocity-astro/cms-ui check:stories` |
| New migration | `pnpm --filter @velocity-astro/cms-db migrations:generate` |

## Where things live

- `packages/cms-core/src/model.ts` — the content model as plain data. No methods.
- `packages/cms-core/src/field-type.ts`, `fields/` — the `FieldType` base class and the built-in types.
- `packages/cms-core/src/fields/blocks.ts` — the `blocks` field type: the sections of a page. `defineBlock` describes one kind of section; the blocks a field allows are stored in its settings (`BlockDef`), each with a permanent id, and a section is `{ id, block, data }` (`BlockValue`).
- `packages/cms-core/src/fields/link.ts` — the `link` field type: an entry of the site (stored as its content type and translation group, never its address) or an address typed by hand. What a menu is made of.
- `packages/cms-core/src/services/` — `SchemaService` and `ContentService`. Every write goes through one of these.
- `packages/cms-core/src/services/form-service.ts`, `submission-service.ts` — forms visitors fill in (`FormDef`: fields like a content type's, who is told, which fields hold the sender's name, email and phone) and what they sent (`Submission`). `submit` is the one write nobody is signed in for.
- `packages/cms-core/src/services/contact-service.ts` — contacts (`Contact`: one per email): made or added to by `noted` when a submission that is not spam arrives, with the team's notes, a timeline of what each person sent, a file of everything held about them (`export`) and `erase`. `catchUp` makes contacts of whoever wrote in before.
- `packages/cms-core/src/services/pipeline-service.ts` — the pipeline (`Pipeline`): the stages a contact moves through, which a site renames, reorders, adds to and removes from. A contact holds a stage's id, the id of whoever on the team looks after it (`Team`, a port the host fills: `AuthTeam` in `cms-auth`) and a day to follow up. The stages the CMS comes with (`DEFAULT_STAGES`) carry no label: the editor names them.
- `packages/cms-core/src/services/deal-service.ts` — deals (`Deal`): what a contact may buy, worth a whole amount of the pipeline's currency, in a stage of the same pipeline. `forecast` adds them up by stage, each open deal counted by its stage's chance (`chanceOf`). A deal belongs to its contact: read and changed with the permissions for contacts, exported and erased with them. The pipeline also names who new contacts from forms are given to (`assignTo`: whoever of them looks after the fewest).
- `packages/cms-core/src/services/custom-fields-service.ts` — the fields a site adds to its contacts and its deals (`CustomFields`), described in the editor as a form's fields are. A contact and a deal hold their values in `data`, by field id; `values` checks what is sent, `byKey` names them for a file handed to a person.
- `packages/cms-core/src/plugin.ts` — plugins: `definePlugin`, and `PluginHost`, which starts each one, gives it its own actor and switches off one that cannot start. Whether a plugin is on, its settings and its own small values live in a `PluginStore` (`plugin_data`), so an owner activates it in the editor with no rebuild, and every running copy follows within seconds. A site names its plugins in `velocityCms({ plugins })`; `cms-astro/routes/plugins.ts` hands them over when the server starts.
- `packages/cms-core/src/ports.ts` — the interfaces adapters implement.
- `packages/cms-core/src/testing/` — in-memory adapters and the contract tests for real ones.
- `packages/cms-db/src/search-index.ts` — search in the same database (FTS5). Its table is a hand-written migration.
- `packages/cms-db/src/tables.ts` — the tables. `migrations/` is generated from it.
- `packages/cms-astro/src/live-loader.ts` — the live loader, for pages rendered on demand. The default way a site reads content.
- `packages/cms-astro/src/preview.ts` — preview links: the middleware that turns a signed token into a preview. The editor posts what is in its form with a preview (`readPreviewDraft`), and the page is drawn once from that (`withPreviewDraft`) and kept nowhere; `routes/preview-client.js.ts` is the script that page runs so a click on a section finds it in the form.
- `packages/cms-astro/src/integration.ts` — what `velocityCms()` adds to a site. `routes/` holds the pages it injects: they ship as source and are compiled with the site, because they must see the site's own files. Keep them thin; logic goes in `src/`, where it is type-checked and tested.
- `packages/cms-astro/src/editor.ts` — `EditorHost`: the editor's page (`admin-files.ts`), the API and sign-in wired over the site's one connection. `site-editor.ts` makes the site's one host and decides which address links are made for. `cli.ts` is the `velocity-cms` command (`bin/` only starts it).
- `packages/cms-astro/src/hosted.ts` — many sites from one running copy, for a host such as Velocity Cloud. A `SiteRegistry` (named by `velocityCms({ sites })`) says which `HostedSite` a host name belongs to: its own database, secret, address and uploads. `hostedRequest` chooses the site before anything else runs and draws the page inside it (`inSite`, `readInSite`); `currentSite()` is what the connection, the secret, the editor's address, uploads, forms and kept pages ask. `examples/starter` has `npm run check:hosted`, which CI runs.
- `packages/cms-astro/src/init.ts` — `velocity-cms init`: sets a site up in its folder (a secret and the local address in `.env`, both and the database's folder kept out of git, the integration in the Astro config). It adds only what is missing, never changes a value that is there, never prints the secret, and edits a config only when it has exactly one `integrations: [` list. `loadCmsEnv` is how the integration brings `VELOCITY_CMS_*` from `.env` to the server while developing and building.
- `packages/cms-astro/src/page-head.ts` — `pageHead(Astro, head)`: what a page says to search engines after the plugins' rules (`cms-core/src/pages.ts`). A template calls it where it writes its title and description. It finds the entry a page is for from the page's address.
- `packages/cms-astro/src/entry-page.ts` — `entryPage(Astro, { types })`: the entry whose own page is at the address being drawn, which is how one route of a site draws every page built in the editor. `entryPageAddresses` lists them for the sitemap, search and share images (`velocityCms({ entryPages })`). The template keeps the map from block key to component and draws the sections itself.
- `packages/cms-astro/src/menu.ts` — `menuLinks(Astro, { type, field })`: a menu people edit in the CMS (a list of label and link on an entry), as links for the page being drawn. It never throws, and answers with none when the page's language has no menu, so the template shows its own links. A link may hold columns of links (`columnsKey`), which a template draws as a large menu; a column may say `show`, a name the template fills with something of its own, such as every neighborhood.
- `packages/cms-astro/src/single.ts` — `single(Astro, type)`: what a single page of the CMS holds, by field key, for the page being drawn: a site's settings (its name, logo, phone number), which every page reads. The page's language first, then the first language's. It never throws, and answers with nothing until something is published, so the template uses its own values.
- `packages/cms-astro/src/link.ts` — `linkTo(Astro, value)`: where a `link` field's value leads for the page being drawn (a button in a section). An entry's address today in the page's language, a typed address if a site may link to it, and nothing otherwise. It never throws. `linkResolver` is the same for many links at once, and what `menuLinks` uses.
- `packages/cms-astro/src/form-post.ts` — `FormPosts`: the one address anyone may post to (`/api/cms/submit/<form key>`, `routes/submit.ts`), for a plain form or a script. It checks where a post comes from, how large it is and how many one address has sent, marks as suspected a post that filled the hidden field or carries no true mark of when its form was drawn, and emails the form's people (`NoticeMailer`). `site-forms.ts` has `siteForm(Astro, key)`: a form for the page being drawn, with where it posts and the hidden fields to send along. A section of a page chooses its form with a field of type `form` (`FormField`, which stores the form's id), and its block asks `siteForm(Astro, { id })`. `routes/form-client.js.ts` is the script (`/cms-form.js`) that sends a marked form in place and writes each problem under its field, as text.
- `packages/cms-astro/src/loader.ts` — the Content Layer loader, for sites that choose a fully static build.
- `packages/cms-api/src/api.ts` — the CMS over HTTP: `CmsApi.handle(request)` answers with a `Response`. Routes hold no rules; they check the shape of what was sent and call a service. `authenticator.ts` is how it learns who is asking; `http.ts` maps each refusal to a status and a code.
- `packages/cms-auth/src/auth.ts` — sign-in: `CmsAuth` wraps Better Auth (email links, passkeys) and is the only file that knows it. `client.ts` is the browser's side and imports nothing. `mailer.ts` is how a site delivers the links. Its tables are `auth_*` in `packages/cms-db/src/auth-tables.ts`.
- `packages/cms-ui/` — the editor's design system. `src/tokens/tokens.css` holds every colour, size, radius, shadow and duration; `src/styles.css` turns them into the Tailwind theme and switches Tailwind's own palette off; `src/components/` and `src/patterns/` hold one folder per part; `component-registry.json` lists them all; `scripts/check.mjs` enforces the rules below.
- `packages/cms-admin/` — the editor's screens, a React app. `src/client/admin-client.ts` is the only way to the server (`queries.ts` wraps every request, `http-client.ts` is the one a real site uses); `src/messages/en.ts` holds every word; `src/app/` has the routes, addresses and frame; `src/screens/` has one folder per screen; `src/fields/` has the control for each kind of field, looked up by the name a field type gives as `editor`; `src/fields/settings.tsx` has the form for each field type's settings in the content type builder (`screens/ContentTypes`, `screens/ContentType`), looked up by the field type's name; `src/testing/` has the in-memory server the tests and the preview (`pnpm --filter @velocity-astro/cms-admin dev`) run against.
- `packages/cms-admin/src/fields/BlocksControl.tsx` — the control for a page's sections: a `SectionList` of the entry's sections, each opening to its block's fields, and an `OptionPicker` of the blocks the template has today. `block-icons.ts` holds the icons a block can name.
- `packages/cms-admin/src/screens/EntryEditor/PagePane.tsx` — the page beside the form (`Workbench`, `PagePreview`), shown for an entry that has a page and a field whose control says `showsPage`. `fields/page-focus.tsx` is how the form and the page tell each other which section is being looked at.
- `packages/cms-admin/src/screens/Forms`, `screens/Form` — the forms a site has, and one form: what it was sent (`Submissions.tsx`, new first, then handled and spam), its fields (`FormFields.tsx`, drawn by the shared `FieldSetEditor`) and its settings. A form's fields are saved all at once, each with its id, and only kinds a visitor can fill in are offered (`FieldTypeInfo.takesSubmissions`).
- `packages/cms-admin/src/screens/Contacts`, `screens/Contact` — the people who wrote to the site (a list with a search, adding one by hand), and one contact: details, the timeline of what they sent and the team's notes, export and erase. For owners and editors.
- `packages/cms-admin/src/screens/Contacts/PipelineBoard.tsx`, `StagesDialog.tsx`, `pipeline.ts` — the contacts as a board by stage (the `Board` pattern: a card is dragged, or moved from its menu), the window the stages are edited in, and how a stage, an owner and a day to follow up are said. `screens/Contact/ContactWork.tsx` sets the three on one contact; `screens/Home/FollowUps.tsx` lists what is due for whoever is signed in.
- `packages/cms-admin/src/screens/Deals` — every deal as a board by stage with what is open, forecast and won, and the window a deal is added, changed and deleted in (`DealDialog.tsx`). `screens/Contact/ContactDeals.tsx` lists one contact's deals.
- `packages/cms-admin/src/screens/Deals/deal-subject.tsx`, `screens/EntryEditor/EntryDeals.tsx` — what on the site a deal is about (a kind of content, then one of its entries, by name), and the card on an entry that lists the deals about it.
- `packages/cms-admin/src/fields/FieldSetEditor.tsx`, `FieldSetDialog.tsx`, `field-set.ts` — a list of simple fields edited as a whole (`FieldSet`): a form's (`screens/Form/FormFields.tsx`) and the custom fields of contacts and deals (`fields/CustomFieldsDialog.tsx`). `fields/custom-values.tsx` fills custom fields in on one contact or deal, with the controls entries use.
- `packages/cms-admin/src/plugins/` — what plugins add to the editor. `plugin-editor.tsx` loads each running plugin's editor file (`definePlugin({ editor })`, served by the site at `/admin/plugins/<name>.js`) and hands it `{ React, ui, client, register }`; `plugin-ui.ts` names the design system parts a plugin gets; `PluginBoundary.tsx` keeps a plugin's fault to its own part of the screen.
- `packages/cms-plugins/` — the plugins that come with the CMS (`catalogue`), each in its own folder. `cms-astro/src/site-plugins.ts` loads them on every site after the site's own, switched off until an owner activates one. `seo/` is the first: `analyse.ts` judges an entry, `plugin.ts` is the server side, `editor.ts` the editor's part. `webhooks/` sends what happens (a form submitted, a contact or a deal changed, a page published) to the addresses an owner lists, signed when a signing secret is saved. `mailchimp/` adds whoever sends a form to a Mailchimp audience: the API key is a secret and the only thing that chooses the host (`mailchimpHost`), someone already in the audience is never updated, and an owner may name the forms and a yes or no field that asks for consent. `slack/` posts to a channel when a form is sent or a contact is made: the webhook address is a secret, only `hooks.slack.com` is posted to (`slackAddress`), and a message names the person only when the owner asks. `hubspot/` copies contacts to HubSpot one way, matched by email, to one fixed address (`HUBSPOT_UPSERT`) with a private app token kept as a secret.
- `packages/velocity-cms/` — the `npx velocity-cms` command for a site that does not have the CMS yet: `init` installs `@velocity-astro/cms-astro` with the site's package manager, and every command is handed to the CMS the site has. No build and no dependencies.
- `scripts/version.mjs`, `scripts/publish.mjs`, `.github/workflows/release.yml`, `CHANGELOG.md` — a release: every package gets one version, the changelog names it, and the workflow, run by hand from main, rehearses unless told to publish. It holds no key: each package on npm trusts this workflow to stage a version, which is public once an owner approves it on npmjs.com.
- `examples/starter/` — a small site on the CMS that is plain Astro: its model and seed (`cms/`), one component per section, and `npm run check`, which CI runs to prove a site works from an empty database. Keep it small enough to read in one sitting; it is what the README tells people to run.
- `prototypes/` — phase 0 experiments. Scripts here may be rough; packages may not.

## Rules

- **Dependencies point inward.** `cms-core` imports Zod and nothing else: no Node built-ins, no Drizzle, no Astro. Need the outside world? Add an interface to `ports.ts` and implement it in an adapter package. `eslint.config.js` enforces this; add a boundary block when you add a package.
- **Every write follows four steps, in order:** permission check, validation, save with history, event. Don't write to a repository from anywhere but a service.
- **Classes for behaviour, plain objects for data.** Don't add methods to `Entry`, `ContentTypeDef` or `FieldDef`. They are stored, sent to the browser and compared.
- **Two versions per entry.** `data` and `slug` are what is being worked on; `published` is what visitors see. A save never changes `published`; only `publish` does. The site reads with `toPublic(type, entry)`, and only a preview passes `'working'`.
- **An entry is moved to the trash, never deleted outright.** `trash` takes it off the site (announced as unpublished, so kept pages and search follow), out of every list but the trash (`EntryQuery.trashed`), and frees its slug; `restore` brings it back as a draft. Only an entry in the trash can be deleted for good (`delete`, which needs `entry:delete`), and that removes its history too. An entry in the trash cannot be changed.
- **A copy of an entry is a draft of its own.** `duplicate` takes what the original holds now, never what is published, starts a new translation group, and finds a free slug (`-copy`, `-copy-2`). A single page has no copy.
- **History only grows.** An earlier version is brought back as a new save of the working version (`revert`): no revision is removed or rewritten, the slug stays as it is today, what visitors see waits for a publish, and a value today's fields would not take is left as it is now.
- **A time to publish is kept on the entry, and the site looks for what is due.** `schedule` needs the entry fit to publish today and sets `publishAt`; what goes out is what the entry holds when the time comes. A site may have no clock of its own, so `EditorHost.publishDue` is asked on every request for a page (`routes/due.ts`) and looks at most every half minute, and a scheduled job may call `/api/cms/schedule` with the site's secret. An entry no longer fit when its time comes is taken off the schedule with the reason kept on it (`publishProblem`), never tried for ever.
- **What a visitor sends is personal data.** A submission is read only through `SubmissionService`, by someone with `submission:read`; a plugin hears of one only if it declared that permission (`EVENT_NEEDS`). Nothing from a submission reaches a page, a cache, the search index or a log. `submit` keeps only the form's own fields, each turned into its value and checked by its field type (`takesSubmissions`, `fromSubmitted`), and a closed form answers as one that is not there. A person's submissions can be exported (`export`, safe to open in a spreadsheet) and erased (`erase`), and a form may say how long they are kept (`purge`).
- **A contact is personal data too.** Contacts are read with `contact:read` and changed with `contact:manage`, through `ContactService` only, and never reach a page, a cache, the search index or a log. A form never overwrites what the team typed about a person; it only fills what is missing. A contact that cannot be made never loses the submission. Forgetting a person, from Forms or from Contacts, removes the contact, the notes and everything they sent. A file of contacts comes in through `ContactService.import`, at most 200 rows a call (the editor reads the CSV in the browser, `lib/csv.ts`, and sends it in parts): someone already here only gains what they lack, a row that cannot be taken is reported by its place and never by what it held, and each save is announced as `imported`, so nothing treats a file as news line by line.
- **A stage's id is permanent, and a contact is always in a stage of the pipeline.** A rename or a new order changes nothing a contact holds; contacts in a stage that is removed move to the first, which is always open. Who looks after a contact must be on the team and allowed to read contacts. A move to another stage is kept beside the contact's notes (`ContactNote.moved`, with who made it) and shown on the timeline; it goes when the contact is erased.
- **A deal is about an entry by the entry, never its name or address.** A content type says whether deals can be about its entries (`forDeals`, set in the builder or by a template); a deal then holds the type's id and the entry's translation group (`DealSubject`) beside its own words. The subject is checked only when it is set or changed, so a deal keeps one whose entry has gone or whose type no longer takes deals. What an entry's deals are is shown in the editor only to those who may read contacts, and never reaches the site.
- **A custom field is a simple kind, never required, and keeps its id.** Only kinds a visitor could fill in (`takesSubmissions`) can be added to contacts and deals, since each has one value and a control. None can be required: a contact made by a form cannot be asked for more. A removed field is marked `deletedAt` and what it held stays on each contact and deal; a change that does not name a field leaves its value alone, and an empty one clears it. A form may say which of its answers fills which custom field of a contact (`FormDef.fills`): only a field of the same kind, only where the contact holds nothing yet, and an answer the field would not take is left out.
- **The address that takes a form's post trusts nothing it is sent.** Every check lives in `FormPosts`, not in the route. Nothing a visitor typed is written back into the page that answers them, a suspected post is kept as spam and answered like any other, and a notice that cannot be sent never loses the submission or puts its content in a log. A visitor is never emailed: only the addresses a form names are.
- **A page that draws a form is cleared when the form changes.** `EditorHost` treats a form saved, trashed, restored or deleted like a publish, so a kept page never shows fields the form no longer has. A form that is closed or gone leaves its section out; the page is never lost over it.
- **Which entry a submission is about is the site's word, never the visitor's.** A page says it with a mark signed for that form (`siteForm(Astro, key, { about })`, `aboutMark`), or the server finds the entry whose own page the post came from (`entryAt`). A form that says `startsDeal` then starts a deal about that entry for the sender (`DealService.started`), when the entry's type takes deals and they have no open deal about it; it is worth nothing until someone says, and a failure there never loses the submission.
- **A draft sent with a preview is drawn and forgotten.** It is read only from a post by the site's own pages with a valid preview token, shown to the one who sent it, never cached and never stored. Whatever reads an entry for a page passes it through `withPreviewDraft`.
- **Drafts never leak.** Anything that shows working versions must check `isPreview()`, must not be cached, and must not feed search, the sitemap or share images.
- **A template's content types are described in code and applied with `schema.define`.** It may run on every deploy: a field keeps its id by key, so content stays, and fields the description leaves out are kept. A type also names the field its entries are called by (`titlePath`) and the sections the editor shows (`sections`).
- **Field ids are permanent.** Entry data is keyed by field id, never by key. A rename changes the key only. A removed field is marked `deletedAt` and its data is kept.
- **A plugin gets the public surface and nothing else.** What `setup` receives is `PluginContext`: add to it deliberately, because every addition is a promise to plugin authors (`PLUGIN_API_VERSION`). A plugin writes through the services as its own actor, with only the permissions it declared, and a failure in one is caught, counted and shown under Plugins; it never stops a save or a publish. A plugin's own addresses live under `/api/cms/plugins/<name>/` and keep every API rule; its settings are fields, drawn by the editor with the controls entries use.
- **In the editor, a plugin gets what it is handed and nothing else.** Its editor file is one prebuilt module with no React of its own. It adds screens, panels on an entry and field controls through `register`, reaches only its own addresses through `client`, and builds from the parts in `plugin-ui.ts`. Each part and each method there is a promise to plugin authors: add on purpose, never remove within one `PLUGIN_API_VERSION`. Whatever a plugin draws is wrapped in `PluginBoundary`, and a file that fails to load leaves the plugin out and the editor running.
- **A plugin's key or password is a secret, never a setting.** It is named in `definePlugin({ secrets })`, saved by an owner one at a time (`PluginHost.setSecret`), sealed with the site's secret before it is stored, and read only by the plugin (`cms.secrets.get`). Nothing sends it back to the editor: the settings say only that one is saved.
- **Work that reaches another service goes through `cms.tasks`.** A plugin defines a kind of work and adds pieces of it; the host tries each at once, again after a minute and at longer waits for about a day (`TASK_RETRY_AFTER_MS`), and shows every piece under Plugins with a way to try a failed one again. What a piece carries may be personal data: it is dropped the moment the work is done, is never shown or logged, and a failed one keeps it seven days at most. A label and an error say where, never what or who. Waiting work is looked for wherever plugins are used (`PluginHost.work`), since a site may have no clock of its own.
- **Something sent out of the site goes only to a public `https` address** (`deliveryAddress` in `cms-plugins/src/webhooks`): never this machine, a bare number or a redirect, and an error names the host alone, since an address may hold a key. A name a person typed is also looked up before anything is sent (`cms.net.isPublic`, which the site fills with `NameLookup`): a public name that leads to a private machine is refused (`isPrivateAddress`).
- **A plugin that ships is built like any other.** Everything in `cms-plugins` uses only `definePlugin` and what its editor file is handed, says `enabledByDefault: false`, and declares the fewest permissions it can. If one needs something the surface lacks, the surface gains it for everyone, on purpose. Its editor part is a function sent to the browser as text (`fn.toString()`), so it and anything sent with it must stand alone: arguments only, no imports, no helpers from the file.
- **A plugin changes a page only through its head, and only as text.** `pages.head` rules answer with a title, a description and whether the page is listed; `PageHeads` takes plain text and a yes or no and nothing else, and the template writes them as text. A rule that fails leaves the page as the template made it. `pageHead` never throws: a page is not lost over its description. A plugin that changes what pages say calls `pages.changed()`, so kept pages are cleared.
- **A page is sections of data, never markup.** A section says which block it is by the block's id and holds that block's values by field id; the site receives the block's key and the values by key, and the template's own component draws it. A block's look is a choice among named values, not a free size or colour. Blocks are described in code: what a description leaves out is retired or marked removed, never deleted, and sections made from a retired block are kept and left off the site.
- **A slug is one part of an address unless the type says otherwise.** A type whose address pattern says `[...slug]` (`/[...slug]`) takes slugs of several parts, such as `services/roofing`, so pages can sit under pages; every part is a slug by itself (`isSlugPath`). Nothing else may put a slash in an address. The entry whose slug is `index` is the page at the top of such a pattern: with `/[...slug]`, the home page, at `/` and nowhere else.
- **A link to an entry is stored as the entry, never as its address.** The site works the address out when it draws the page, in the page's language, and leaves out a link whose entry is not published. A typed address must pass `isSafeLink`.
- **No switch on field type.** Behaviour that differs by field type is a method on `FieldType`.
- **A new adapter must pass the contract tests** in `@velocity-astro/cms-core/testing`. Add a case there when you find behaviour an adapter could get wrong.
- **Migrations only move forward.** Never edit a generated migration that has shipped.
- **Errors are for people.** Throw a `CmsError` subclass with a message that says what happened and what to do, naming fields by key.
- **No `any`** and no hardcoded user-facing strings outside error messages.
- **Live by default.** A published change must be visible at once. Pages that show CMS content are rendered on demand, cached with `Astro.cache.set()` under the tags the live loader provides, and cleared by tag on publish. Never add a rebuild step to the publish path.
- **The editor is served ready-made.** `cms-admin` builds it once (`build:app`, into `app-dist/`), and a site serves those files at `/admin`; the site's own bundler, React and styles never touch it. Its settings are written into the page as JSON. Its page allows scripts only from the site itself.
- **Links are made for the configured site, never for the request's host.** On a deployed site the address comes from `site` or `VELOCITY_CMS_ORIGIN` (`editorOrigin`). Whoever sends a request chooses its `Host` header. The site reads its own pages (for search and share images) the same way: from `pagesOrigin`, which takes the request's address only when the site is known by it, and never from a path that leads off the site.
- **On a server that runs many sites, nothing is read for "the" site.** Whatever a site owns (its database, secret, address, uploads, and anything kept in the server's memory about it) is reached through `currentSite()` or filed under `siteKey()`, never read from the environment or kept in one module-level value. Work begun for no site throws (`NoSiteError`): it must never fall back to some site's content. The registry alone says which site a host name is, a kept page carries its site's tag (`siteCacheTag`), and the copy must list the host names it answers to (`security.allowedDomains`), since kept pages are filed by the address Astro believes. A new piece of per-site state gets a case in `hosted.test.ts` that tries to cross.
- **A route the integration adds says whether it may be cached.** Sites cache pages rendered on demand by default, so the editor's routes call `cache.set(false)` first: a cached answer would show one person's session or a draft to the next.
- **Zod** is a peer dependency pinned to the range Astro ships, so the same schemas serve the CMS and Astro's collections.

## API rules (`cms-api`)

- **Web standards only.** `Request` in, `Response` out. No Node, no Astro, no framework, so it mounts anywhere the site runs.
- **No rules in a route.** A route parses with Zod (`strictObject`, so an unknown property is refused), calls one service as the person who asked, and returns JSON. A rule that seems to belong in a route belongs in `cms-core`.
- **Every route but `GET /session` needs a session**, and a change must come from the site's own pages as JSON (`#requireOwnPage`).
- **A body is read with its limit in force** (`#bytes`), never whole and measured afterwards: a request sent in parts says no length.
- **Errors have one shape:** `{ error: { code, message, issues? } }`. A refusal keeps the service's own words. A fault answers 500 with nothing about the inside, and goes to `onFault`.
- **Nothing is cacheable.** Every response is `no-store`: the API serves drafts.
- **A new method on `AdminClient` gets a route here, a method on `HttpAdminClient`, and a case in `adminClientContract`** (`cms-admin/src/testing`), which both clients run.

## Sign-in rules (`cms-auth`)

- **One file knows the library.** Everything else sees `Authenticator`, `handle`, and the methods on `CmsAuth`. Don't import `better-auth` anywhere else, and don't reach into its internals: write to the `auth_*` tables this package owns.
- **No passwords, no sign-up.** People are invited by an owner. The first owner is made by `createFirstOwner`, which refuses once anyone exists.
- **Never email a stranger, and never say who has an account.** A request for a link is answered the same way whoever the address belongs to. The same way includes how long it takes (`answerAfterMs`) and what happens when the email cannot be sent, which only the log hears of. One address is emailed three links in ten minutes at most.
- **A link never leaves the site.** Where a link lands afterwards must be a path here; `#deliver` checks it whatever the library does.
- **The role lives on the person and only an owner changes it.** A role this version does not know grants nothing.
- **`client.ts` imports nothing**, so the editor never ships server code. ESLint enforces it.

## Design system rules (`cms-ui`)

`pnpm lint` fails when one of these is broken, and says which file and how to fix it.

- **Four layers:** tokens → components → patterns → screens. A layer uses only the layers before it. Screens (`cms-admin`) contain no styling and no raw interactive HTML.
- **One folder, six files:** `X.tsx`, `X.variants.ts`, `X.stories.tsx`, `X.test.tsx`, `X.md`, `index.ts`. Nothing else.
- **Parts are closed.** No `className`, no `style`, no props passed through. A new look is a new variant, so every screen gets it.
- **Class names live in `X.variants.ts`** (CVA), never in the component file. Classes that several parts share (a field's label, a floating panel) live in a file at the root of the layer, such as `components/field.ts`, and are checked the same way.
- **Tokens only.** Every class must resolve against the theme in `styles.css`. No arbitrary values (`w-[13px]`), raw colours or raw sizes. A new value is a new token in `tokens.css`, for light and dark.
- **Behaviour comes from React Aria Components.** Don't hand-write focus handling, keyboard handling or ARIA attributes. Style states with its data attributes (`data-hovered:`, `data-focus-visible:`, `data-disabled:`).
- **Motion comes from the `motion-*` utilities** in `styles.css` (`motion-pop`, `motion-sheet`, `motion-float`, `motion-rise`, `motion-press`), which use the duration and easing tokens, so everything of one kind moves the same way and stops for people who ask for less motion. Don't write a one-off animation in a part.
- **Icons are Lucide**, passed as a prop and hidden from screen readers. The words carry the meaning.
- **No words of its own.** A part shows the text it is given; it has no built-in English.
- **Registry in sync.** Add the part to `component-registry.json` (group, description, example, `uses`) and export it from the layer's `index.ts`. The story title is `Components/<group>/<Name>` or `Patterns/<group>/<Name>`.
- **Every part is tested** for what it does with a keyboard and a pointer, and with `expectAccessible()`. Every story must pass WCAG 2.1 AA in light and dark (`check:stories`). A story that shows something open (a dialog, a list, a tooltip) is tagged `['!autodocs', 'overlay']`, so it is checked once open and kept off the docs page.
- **Something missing?** Add it to `cms-ui` first, with its six files, then use it. Don't build a one-off in a screen.

## Screen rules (`cms-admin`)

ESLint fails when one of these is broken.

- **Screens are built only from `@velocity-astro/cms-ui`.** No `className`, no `style`, no HTML elements, no imports of React Aria or Tailwind. If a part is missing, add it to `cms-ui` first.
- **No words in screens.** Every string a person reads lives in `src/messages/en.ts` and is read with `useMessages()`. A message with a value in it is a function.
- **The server is reached only through `AdminClient`,** and screens call it only through the hooks in `client/queries.ts`, so each request has one cache key.
- **Addresses come from `app/paths.ts`.** Don't write a path by hand in a screen. Go to one with `useGo()` (`app/use-go.ts`), so every change of screen moves the same way.
- **A dialog is seen leaving.** One made anew each time it opens closes with `useClosing(onClose)` (`lib/use-closing.ts`) and is taken away once it has gone, not unmounted while open.
- **Every request has three states on screen:** loading, failed (with what went wrong and a way to try again) and done, which includes an empty state. Loading is `LoadingState` with the `shape` of what is on its way (`app/RequestState.tsx`), so the screen keeps its layout; a spinner is only for before there is a layout to keep.
- **No switch on field type here either.** A field is drawn by the control registered under its field type's `editor` name (`fields/controls.tsx`), and set up in the builder by the settings registered under its type (`fields/settings.tsx`). A new kind of field is a new control, registered; a field with no control is shown by name with a note, and its content is kept. A list asks its items' control what a value is called (`titleOf`): with an answer its items are rows that open (`SectionList`), without one they are laid out in full (`Repeater`).
- **A form holds what was typed; the server holds what is saved.** Send `expectedRevision` with every save, show a refusal's `issues` on the fields they name, and never drop what the person typed because a request failed.
- **What a visitor wrote is shown as text, and only to those who may read it.** The screens for submissions are for owners and editors, draw every answer with `Text`, and keep nothing of it outside the request cache. An export is handed to the person as a file (`lib/download.ts`) with a word about keeping it safe.
- **Screens are tested through the whole app** with `renderApp(path, …)` against `MemoryAdminClient`: find things by role and name, act as a person would, and check what they would see.
